Slide 03 · Core Concept

Not a quiz.
A conversation.

Each turn, Claude returns only the slots it just extracted — a delta. The client accumulates them over 6 stages until the full picture is complete.

  • Claude never re-asks answered slots
  • Context from earlier stages compresses later stages
  • Accumulation lives on the client — no server state
Stage flow → slot accumulation
01
service_id service_name, price, billing_cycle
02
motivation primary_motivation, clarity
03
history_check subscription_history
04
expected_usage expected_frequency
05
budget_fit budget_feel
06
overlap_decision overlap_level
→
All δ merged = complete slots
Deterministic scorer runs. No API call needed.

Slide 04 · Protocol Detail

What Claude
returns.

Every response is JSON-only. The client parses slots_delta and merges it into accumulated state. Flags and aha moments are side channels.

Claude response schema (one turn)
// Stage 4 — expected_usage
{
  "stage": "expected_usage",
  "bubbles": ["Makes sense for commuting"],
  "question": "How often realistically?",
  "slots_delta": {
    "expected_frequency": 4.5
  },
  "flags": { "contradiction": false },
  "aha": { "triggered": false }
}
Client accumulation logic
  • Merge: slots = { ...slots, ...slots_delta }
  • Guard: only advance stage when required slots are filled
  • AHA: if triggered, inject insight bubble before next question
  • Finish: when all 6 stages complete → run scorer locally

Slide 05 · Persona System

How we
classify you.

Setup asks 4 scenario questions. Claude assigns a subscriber type and trait tags. This shapes every future audit score.

  • Scenario questions → AI analysis → subscriber type + trait tags
  • PAC (Persona Alignment Coefficient): 0.7 weak → 1.0 neutral → 1.3 strong
  • PAC multiplies need_fit score — same service, different outcome
5 subscriber types
⚡
power_user
Uses every feature, maximizes value. High engagement across multiple subs.
PAC: 1.3 (strong match boost)
✂️
essentialist
Prunes ruthlessly. Keeps only what's actively used weekly.
PAC: 0.9 (conservative)
🔥
binge_cancel
Subscribes for a specific show or project, then cancels.
PAC: 0.8 (risk-flagged)
🎯
free_trial_tester
Always on free trials. Converts only for clear long-term value.
PAC: 1.0 (neutral)
💰
budget_hawk
Price-driven. Every dollar is tracked. Overlap and cost are the primary filters.
PAC: 1.1 (budget-weighted scoring)

Slide 07 · Why Workbench

The notebook
became a
bottleneck.

4 separate Jupyter parts worked for early prototyping. But prompt iteration got painful fast.

Pain points with Notebook workflow
Changing a prompt = re-run the entire chain
Parts 1–4 are sequential · one edit invalidates downstream cells
No way to see conversation + scores simultaneously
Had to scroll between output cells · lost context constantly
Testing a new persona meant manual JSON edits
No import flow · copy-paste from benchmark file every time
LLM Adjuster parameters buried in cell vars
No UI to tweak weights · had to hunt through code for each knob
→
Built Workbench to close the iteration loop in one interface

Four zones.

Slide 11 · Debug System

Fix upstream
before looking
downstream.

The system has three layers. When a score is wrong, always verify slot extraction before touching the scorer — bad input makes good code look broken.

Three-layer debug stack
L1
Slot Extraction
Are the right slots being filled? Check slots_delta per turn in Workbench Chat panel.
↓
L2
Rule Engine (Deterministic)
Is the scorer reading slots correctly? Inspect breakdown: need_fit, usage, budget_fit, overlap, risk.
↓
L3
LLM Adjuster
Is the ±8 LLM adjustment distorting correct base scores? Check adjuster output vs raw scorer total.
Current status
P0 motivation_clarity slot missing in some edge cases → wrong need_fit
P1 binge_cancel PAC coefficient needs recalibration against P003 benchmark
P2 Adjuster occasionally pushes scores past badge threshold boundaries
